# 分阶段检索协议（P0–P6）

> 这份文档是这个项目最可复用的部分：**它是一套方法论，不依赖 `aml` 也能用**。
> 就算你不用这套代码，把「阶段表 + prompt 片段」抄进你的 agent 规则文件，也能立刻受益。

## 它解决什么问题

绝大多数"给 agent 加记忆"的实现，都默认这样一种用法：**任务开头检索一次**，把结果塞进上下文。

真实工作里这会漏掉三类时刻：

1. **方案定型后**才需要的方法论（开头不知道该查什么）
2. **动手改某个文件/工具/平台之前**才需要的具体约定（开头查的是"这个项目"）
3. **报错之后**才需要的同类踩坑记录（开头根本不知道会报错）

于是"检索"应该绑在**任务生命周期的节点**上，而不是绑在任务的开头。
每个节点需要的信息不同、**能承受的预算也不同**（动手前你只要 3 条 600 字，定方案时你要 1500 字）。

## 三条铁律

| 铁律 | 含义 | 反例 |
|---|---|---|
| **① 部分** | 每次只取该阶段要的那一点，绝不把整库读进来 | "把所有相关知识都给我" |
| **② 分阶段** | 不是开头查一次，而是每进入新阶段/新文件/新工具/新领域就各查各的 | 任务开头检索一次就完事 |
| **③ 不重复** | 同一阶段 + 同一查询在冷却期内不重查；要重查就换措辞或换层级 | 反复查同一个词，把预算榨干 |

## 阶段表

| 阶段 | 什么时候 | 要回答的问题 | 查什么 | 预算（条数 / 字数） |
|---|---|---|---|---|
| **P0 定位** | 接到任务、**还没动手** | 这属于哪个项目/领域？以前做过类似的吗？ | ① 跨项目沉淀（`kind:knowledge`）② 本项目最近历史（`project:<名>`）③ 索引/目录路由（决定读哪一块，而不是全库读） | ≤6 / ≤1200 |
| **P1 定方案** | 准备**定方案/选型/口径** | 有没有现成方法论、坑、决策先例？ | `domain:*` 的方法论与 pitfall；要细节再读对应的沉淀文件 | ≤5 / ≤1500 |
| **P2 执行前** | **每次动具体东西之前**（改文件、跑命令、调接口、写内容） | 这个具体操作的正确姿势、约定、陷阱？ | 目标文件/工具/平台的**具体**约定（查具体名词，别写整句） | ≤3 / ≤600 |
| **P3 卡住** | 工具失败、结果异常、越改越乱 | 这个错以前谁踩过？ | `ktype:pitfall` + 错题集 + 错误码/关键句的**精确**检索 | ≤5 / ≤1000 |
| **P4 决策** | 要在方案之间选、要改口径 | 以前怎么定的？为什么？后果是什么？ | `ktype:decision`；先查沉淀，再查本项目 | ≤4 / ≤1000 |
| **P5 自检** | 交付/汇报**之前** | 我漏了什么？验收标准是什么？ | `ktype:checklist` + 本项目近期验收/驳回记录 | ≤5 / ≤1000 |
| **P6 写回** | **每阶段收尾**，不只是任务结束 | 这次有什么值得留下的？ | 写：可复用经验 → `kind:knowledge` + `domain:*`；项目事实 → `project:<名>`；新坑 → 错题集 | 1–3 条 |

**P2/P3/P4 会反复触发**——这是它与"开头查一次"的本质区别。

## 层级优先与命中即停

检索结果按三层给，**上层命中就停**，不往下再翻：

```
① 跨项目沉淀（kind:knowledge + reusable:true + domain:*）   ← 最值钱：A 项目的经验用在 B 项目
② 本项目历史（project:<项目名>）                            ← 具体到这件事的上下文
③ 全库泛查（其余一切）                                      ← 兜底，噪声最大
```

配套的三条：

- **命中即用**：1–2 条相关就够，不追求"查全"。
- **阈值**：明显不相关的宁可不要（相似度太低就别放进上下文——放进去是干扰，不是帮助）。
- **累计预算**：单个任务所有阶段注入的检索内容合计有上限（默认 ≤6000 字），超了只保留最新阶段。

## 检索为空时怎么办

**"没查到" ≠ "没有"。** 只走"语义 + 硬阈值"最常见的故障叫 **false empty**：
库里明明有记录，泛词/同义词查询却返回 0 条，于是调用方误判成"没有历史约定"，重新踩一遍坑。

所以协议要求：**未命中必须解释为什么空**，并给出换招建议。实现上是级联回退：

```
语义@0.80  →  语义@0.72  →  语义@0.65  →  FTS5 关键词  →  LIKE 兜底
   ↑ 严格                                                            ↑ 宽松
```

未命中时的正确输出形态：

```text
（没命中。下面说明为什么，避免把「没查到」当成「没有」）
· 语义返回 42 条，最高分 0.61；达到最松阈值(0.65)的有 0 条
· 可换招：① 换措辞（同义词/术语） ② 放宽 -n ③ 用 --tag domain:xxx 收窄 ④ 用关键词翻原文
```

四种换招：

1. **换措辞**：同义词、上位词、行业术语、错误码原文
2. **放宽条数**：`-n`
3. **收窄标签**：`--tag domain:env-windows` / `--project <名>`
4. **关键词直查**：FTS/LIKE 走原文（语义检索对短查询、专有名词最不灵）

## 工具映射

| 协议动作 | CLI | MCP 工具 |
|---|---|---|
| 按阶段检索 | `aml search "关键词" --phase P2` | `search(query, phase, project, tag, n)` |
| 看未命中原因 | `aml search ... --explain` | 同上（返回文本里带诊断段） |
| 看阶段定义与预算 | `aml search --help` / 本文档 | `phase_spec(phase)` |
| 写回知识 | 手动 `aml search` 不行——走 `aml distill` 或直接 `store` | `store(content, tags, metadata)` |
| 结尾播报 | `aml patrol notify --brief` | `brief()` |
| 体检 | `aml doctor` | `doctor()` |

## 可直接粘贴的 prompt 片段

### 精简版（塞进 AGENTS.md / CLAUDE.md，5 行）

```text
【分阶段检索】不是任务开头查一次，而是每个阶段各查各的：
· P0 接到任务：aml search --phase P0 "<任务关键词>"      —— 先看跨项目沉淀，别全库读
· P1 定方案：  aml search --phase P1 "<方案/选型关键词>"
· P2 动手前：  aml search --phase P2 "<文件/工具/平台名词>"  （每次换新东西就再查）
· P3 报错后：  aml search --phase P3 "<错误码或关键句>"
· P6 收尾：    值得留下的经验写回记忆层（可复用的打 kind:knowledge + domain:*）
未命中不要当成"没有"：先看它给的诊断（分数分布）再换措辞/换标签。
```

### 完整版（P0–P6 + 写回规则 + 结尾播报）

```text
【检索纪律】三条铁律：① 只取该阶段要的那一点（别把整库读进来）② 每进入新阶段/新文件/
新工具/新领域就各查各的（不是任务开头查一次）③ 同一查询在冷却期内不重查，要重查就换措辞。

阶段与预算（条数/字数）：
· P0 接到任务、还没动手      → ≤6 条/1200 字：这属于哪个项目/领域？以前做过类似的吗？
· P1 准备定方案/选型/口径    → ≤5 条/1500 字：有没有现成方法论、坑、决策先例？
· P2 每次动具体东西之前      → ≤3 条/600 字： 这个具体操作的正确姿势与陷阱？
· P3 工具失败/结果异常       → ≤5 条/1000 字：这个错以前谁踩过？
· P4 要在方案间选、要改口径  → ≤4 条/1000 字：以前怎么定的？为什么？后果？
· P5 交付/汇报之前           → ≤5 条/1000 字：漏了什么？验收标准是什么？
· P6 每阶段收尾              → 写 1–3 条：可复用经验？项目事实？新坑？

层级优先（上层命中即停）：跨项目沉淀 > 本项目历史 > 全库泛查。
命中即用：1–2 条相关就够；明显不相关的宁可不放（相似度太低是干扰不是帮助）。

【未命中】"没查到"不等于"没有"。看诊断：语义返回了几条、最高分多少、卡在哪一档阈值；
然后换招：① 换措辞 ② 放宽 -n ③ 收窄标签 ④ 关键词直查原文。

【写回分层】
· 可跨项目复用（方法论、坑、工具用法、决策理由）→ kind:knowledge + reusable:true + domain:<领域>，不要打 project
· 只对当前项目成立（进度、客户细节、临时结论）→ project:<项目名>
· 新踩的坑 → 错题集/ktype:pitfall
正文要自包含：脱离本项目也看得懂，不写客户名与一次性链接。

【引用要说出处】说明这条来自哪个 agent、哪个时间、哪一层（沉淀/本项目历史）。
没有命中就直说没查到——**不要编**。

【回答结尾】执行 aml patrol notify --brief：
· 没有输出 → 什么都别提（没变化就不要刷屏）
· 有输出 → 把它作为回答的最后一行贴出来，然后再 --ack
```

## 反模式清单

| 反模式 | 后果 |
|---|---|
| 任务开头检索一次就完事 | P2/P3 时刻该有的约定与踩坑记录全错过 |
| 把整库/整个目录读进来 | 上下文被噪声淹没，真正的结论被稀释 |
| 同阶段同查询反复查 | 挤占预算，而且拿到的还是同一批 |
| 把"没查到"当成"没有" | 重新踩一遍已经记录过的坑（这是最贵的错误） |
| 直接编造历史（"你上次说过…"） | 破坏信任；命中要能说出来源与时间 |
| 收尾不写回 | 这次的经验下次还得重新踩——记忆层永远是空的 |
| 一次性事实混进沉淀层 | 跨项目检索被污染，别人（别的项目）拿到一堆没用的细节 |

## 怎么验证它在工作

1. **`aml doctor`**：检索自测那一项会用一个泛词查一次，确认"查得到"；同时报索引新鲜度、
   向量覆盖率（缺向量的记录**永远搜不到**，这是隐性失效）。
2. **看 false empty 诊断**：随便挑一个你确定库里有的话题，用泛词查。如果返回 0 条但诊断显示
   "语义找回 N 条、最高分 X"，说明阈值偏严——调 `retrieval.cascade` 或换招。
3. **看命中层级**：输出前缀 `[沉淀|domain|日期|分数]`。如果 P0/P1 阶段命中的全是"全库"，
   说明沉淀层还没建起来（继续用 P6 写回）。
4. **抽样回放**：`aml export` 出一份 markdown，人工看几十条知识是不是真的"跨项目可复用"。

## 配置项（`config.yaml`）

```yaml
retrieval:
  cascade: [0.80, 0.72, 0.65]   # 级联阈值：严格 → 宽松；再不行才走关键词
  rel_margin: 0.07              # 只保留与最高分同梯队的（避免"陪跑"挤占预算）
  cooldown_min: 10              # 同阶段同查询的冷却时间（防重复检索）
  result_chars: 200             # 每条截断长度
  phases:                       # 每个阶段的条数与字数预算，按你的任务类型调
    P2: {results: 3, chars: 600}
```

## 出处

这套协议是从一套真实跑了几个月的跨 agent 记忆系统里提炼的（同一个人的 DSH / Claude Code /
Kimi 会话混在一起）。它解决的问题不是"怎么存"，而是**"什么时候取、取多少、取不到怎么办"**。
